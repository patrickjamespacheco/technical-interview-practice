ITwo Pointers

The idea

Two indices walk the same sequence, and the pair of positions is itself the search space. Because each move rules out a whole band of candidate pairs at once, the O(n²) double loop collapses into a single O(n) sweep.

It buys that speed with order: a sorted array, or a structural order such as position in a linked list.

The invariant

Every pair that could still be the answer lies between lo and hi. Advancing lo or retreating hi discards only pairs already proven impossible, so the answer can never be stepped over.

Solution structure

Reach for it when

  • "sorted array, and you need a pair or a triple summing to a target"
  • "do it in place, O(1) extra space" on an array or string
  • "remove duplicates / partition / move zeroes, in place"
  • "is this a palindrome", comparing from both ends inward
  • "detect a cycle in a linked list using constant space"
  • "find the middle, or the nth node from the end, in one pass"

Do not reach for it when

  • Input is unsorted and sorting would destroy the order the answer depends on. Use a hash map in one pass instead.
  • You are maintaining an aggregate over a contiguous run rather than comparing two endpoints. That is a sliding window, and both of its pointers move forward only.
  • Fast/slow only detects cycles where each node has one successor. A general directed graph needs DFS with three-state colouring.

Complexity

O(n) for the sweep, O(n log n) overall if you have to sort first. O(1) extra space, which is usually the point.

Variants

Opposite ends
converge from both sides of a sorted array
Same direction
a read pointer and a slower write pointer for in-place filtering
Fast and slow
cycle detection and midpoint finding in a linked structure
Two sequences
one pointer per sorted list for merge or intersection
k-sum
fix k - 2 indices with loops and two-pointer the remaining pair

IISliding Window

The idea

A contiguous range [left, right] carries an aggregate that is updated incrementally: extending right adds one element, shrinking left removes one.

Recomputing that aggregate for every subarray is O(n²); updating it is O(n) amortised, because each index enters the window once and leaves it once.

The invariant

After the inner while loop, the window between left and right always satisfies the constraint. That is why it is safe to record an answer at the bottom of every outer iteration and nowhere else.

Solution structure

Reach for it when

  • "the longest or shortest contiguous run satisfying a constraint"
  • "at most k distinct characters", "at most k replacements"
  • "a subarray whose sum is at most / exactly a target", with non-negative values
  • "the maximum over every window of fixed size k"
  • "how many requests has this user made in the last 60 seconds"

Do not reach for it when

  • Values can be negative, so shrinking the window no longer reduces the aggregate monotonically and the invariant dies. Use prefix sums plus a hash map.
  • The problem wants a subsequence rather than a contiguous run. That is dynamic programming.
  • Pointers converging from opposite ends is two pointers, not a window: a window's left never passes anything right has not already consumed.

Complexity

O(n) time, each index pushed and popped exactly once. Space is O(1) for a numeric aggregate, O(k) for a frequency counter or a monotonic deque.

Variants

Fixed size k
slide by adding one and dropping one, no inner loop
Longest under a constraint
shrink only while the constraint is violated
Shortest over a constraint
shrink greedily while it still holds, recording each time
Counter window
a dict or multiset for distinct-element constraints
Monotonic deque
window maximum or minimum in O(n) instead of O(n log n)
Time window
evict by timestamp rather than by index

IIITree Traversal (DFS and BFS)

The idea

Every node is visited exactly once. The only real decision is when a node does its own work relative to its children, and that decision is one line's position in the function.

Recursion supplies the stack, so a traversal is four lines and the ordering is free.

The invariant

DFS: when a child's recursive call returns, that entire subtree is finished and will never be revisited, so a node may treat its children's results as final. BFS: the queue always holds nodes in non-decreasing depth, so every node at depth d is dequeued before any node at depth d + 1.

Solution structure

DFS: the three orderings

Preorder (node, left, right) does the node's work before descending. Reach for it when information flows downward: serialising a tree, carrying a path prefix or a running sum into the children, copying a structure.

Inorder (left, node, right) exists for one reason: on a binary search tree it yields the keys in sorted order. That single fact is what makes "kth smallest" and "validate this BST" short.

Postorder (left, right, node) does the node's work last, so the children's answers are already in hand. Use it whenever a node's answer depends on its children's: height, subtree sums, deletion, bottom-up rebalancing. If you catch yourself wanting to return a value up the tree, you are writing a postorder.

BFS: level order

Snapshotting the queue length at the top of each outer iteration is what separates one level from the next. Without that snapshot you get a flat traversal, not levels.

Reach for it when

  • "the depth, the height, or the diameter of a tree"
  • "the sum or the count within every subtree"
  • "return the values level by level", or "the rightmost node of each level"
  • "validate a binary search tree" or "the kth smallest key" (inorder)
  • "the lowest common ancestor of two nodes" (postorder)
  • "serialise and deserialise this tree" (preorder)

Do not reach for it when

  • You need the shallowest leaf, or the minimum depth. BFS answers it on the first leaf dequeued; DFS may spend the whole traversal down one deep branch first.
  • The tree is deep or degenerate (effectively a linked list) and recursion will hit the stack limit. Convert to an explicit stack.
  • The structure has shared children or back edges, so it is a graph, not a tree. Without a visited set the traversal repeats work or never terminates.

Complexity

O(n) time, every node once. Space is O(h) for DFS where h is the height, degrading to O(n) on a skewed tree, and O(w) for BFS where w is the widest level, up to n/2 on a full tree.

Variants

Preorder
top-down, information flows from parent to child
Inorder
sorted order on a BST, nothing else
Postorder
bottom-up, a node consumes its children's results
Level order
BFS with a per-level queue snapshot
Iterative DFS
explicit stack when depth threatens the recursion limit
BST descent
compare and discard one branch, O(h) rather than O(n)

IVGraph Traversal (DFS and BFS)

The idea

The same two engines as trees, plus a visited set, because a graph can reach one node by many routes and can loop back on itself.

That set is not an optimisation, it is what makes the traversal terminate and keeps it O(V + E) instead of exponential.

The invariant

Every node is inserted into visited exactly once, and always before its edges are explored, so each node is expanded at most once even in the presence of cycles. BFS adds a second guarantee: the queue stays in non-decreasing distance order, so the first time a node is reached, it is reached by a shortest path.

Solution structure

DFS: reachability and the visited discipline

Mark on push, not on pop. Marking when you dequeue lets the same node sit in the frontier several times, which is the single most common graph bug.

Cycle detection in a directed graph needs three states, not two: unvisited, on the current path, and finished. Re-reaching a finished node is a diamond, not a cycle. In an undirected graph the test is simpler: a visited neighbour that is not the node you came from.

BFS: shortest path, unweighted only

BFS gives shortest paths only on unweighted graphs, or where every edge has the same weight. With varying weights it returns the path with the fewest hops, which is a different and usually wrong answer; use Dijkstra with a heap, or Bellman-Ford when weights can be negative.

Record the distance at discovery, not at dequeue, and keep a parent map alongside it if you need the route rather than its length.

Reach for it when

  • "nodes and edges", "dependencies", "prerequisites", "who reports to whom"
  • "the minimum number of steps, moves, or transformations"
  • "count the connected components", "count the islands or regions in a grid"
  • "can A reach B", "which services are affected if this one fails"
  • "detect a circular dependency"
  • "a valid order in which to run these tasks"

Do not reach for it when

  • Edges carry weights and you want the cheapest route. BFS will return a confident wrong answer; use Dijkstra (a heap, see VI).
  • A grid problem that maximises a value along a monotone path rather than counting steps. That is dynamic programming, not traversal.
  • The structure is acyclic with a single parent per node. It is a tree, and the visited set is dead weight.

Complexity

O(V + E) with an adjacency list, plus O(V) space for visited and the frontier. A grid is an implicit graph with V = rows x cols and E about 4V, so it is O(rows x cols).

Variants

Reachability and flood fill
DFS or BFS, either works, visited set does the work
Three-colour cycle detection
directed cycles need an on-path state
Topological sort
reversed DFS postorder, or Kahn's in-degree queue
Shortest hops
BFS on an unweighted graph
Multi-source BFS
seed the queue with every source at distance 0
Grid traversal
the implicit graph, four or eight neighbours, bounds check as the edge test

VDynamic Programming

The idea

The problem breaks into subproblems that overlap, and each distinct subproblem is solved once and reused. That reuse is the whole trick: an exponential recursion tree collapses to the number of distinct states.

Tabulation and memoisation are the same recurrence written bottom-up and top-down; pick whichever makes the base cases obvious.

The invariant

dp[i] means exactly one thing, and it is already correct for every index below i at the moment you compute it. If you cannot finish the sentence "dp[i] is the ..." out loud, you do not have a recurrence yet, you have a guess.

Solution structure

Reach for it when

  • "the maximum, the minimum, or the number of ways" over a sequence of choices
  • "can this string be split into words from a vocabulary"
  • "take or skip each item, subject to a capacity or a budget"
  • "the longest increasing / common / palindromic something"
  • "how many distinct paths through this grid with obstacles"
  • the interviewer answers your greedy rule with a counterexample

Do not reach for it when

  • A local rule provably gives the global optimum. Then greedy is correct and DP is a slower right answer; state the exchange argument and take the O(n log n).
  • You need the actual solutions enumerated, not counted or optimised. That is backtracking. DP gives you the value; recovering the choices needs a parent table and a reconstruction pass.
  • The subproblems do not overlap. Then it is plain divide and conquer and the memo table never gets a hit.

Complexity

(number of states) x (work per transition). A 1-D array with O(1) transitions is O(n) time and O(n) space, rolled down to O(1) when only the last two rows matter. Knapsack is O(n x capacity); a grid is O(rows x cols).

Variants

Linear recurrence
take or skip along an array, dp[i] from dp[i-1] and dp[i-2]
Running best (Kadane)
best ending here versus best overall, one pass
Grid paths
counts or costs over a grid with obstacles
0/1 knapsack and subset sum
capacity as the second dimension, iterate capacity downward
Unbounded knapsack
same table, capacity iterated upward so an item can repeat
String segmentation
dp over prefixes against a vocabulary set
Reconstruction
a parallel choice table, then walk it backwards to name the picks

VIHeap / Priority Queue

The idea

A heap hands you the extreme element in O(1) and keeps that true across inserts and removals in O(log n).

Reach for it when you repeatedly need the smallest or largest of a set that keeps changing, and a full sort would be work you throw away.

The invariant

Every node compares no greater than both of its children, so the root is the minimum of the whole structure. In the bounded k-largest pattern the heap holds exactly the k largest elements seen so far, which makes its root the threshold a new candidate has to beat.

Solution structure

Reach for it when

  • "the k largest, k smallest, or k most frequent", and k is much smaller than n
  • "merge k sorted lists or streams"
  • "always process the highest-priority item next"
  • "the running median of a stream"
  • "the next event by time", "the job with the earliest deadline"
  • "the cheapest edge or node to expand next" (Dijkstra, Prim)

Do not reach for it when

  • You need the k largest and then everything else in order anyway. Just sort: same asymptotics, much smaller constant.
  • k is close to n. The O(n log k) advantage evaporates; sort.
  • The maximum over a fixed-size sliding window. A monotonic deque does it in O(n) where a heap costs O(n log n).

Complexity

Push and pop are O(log n); building from an existing array is O(n) via heapify. The bounded k-largest scan is O(n log k) time and O(k) space.

Variants

Bounded k-largest
a min-heap of size k, and its mirror for k smallest
Keyed entries
push (priority, payload) tuples so the comparison is explicit
Two heaps
a max-heap and a min-heap balanced around a running median
k-way merge
seed with one element per list, push the successor on each pop
Lazy deletion
leave stale entries in and skip them on pop
Cheapest frontier
Dijkstra and Prim are this pattern over a graph

VIIBacktracking

The idea

Depth-first search over a tree of partial solutions. Make a choice, recurse, undo the choice, so a single mutable path buffer serves the entire search.

Pruning an invalid partial removes the whole subtree beneath it, and that pruning is what lets an exponential search finish in practice.

The invariant

path holds exactly the choices on the current root-to-node branch, nothing more. Every recursive call leaves path exactly as it found it, which is why the append and the matching pop bracket the recursive call as a pair.

Solution structure

Reach for it when

  • "return all" or "generate every": subsets, permutations, valid placements
  • "find the combinations that satisfy ..."
  • "place n items so that no two conflict"
  • "is there any assignment that works" (return on the first hit)
  • "solve this board or puzzle"
  • the input is small (n up to roughly 20) and the answer is a list of solutions

Do not reach for it when

  • Only the count or the best value is wanted, never the solutions. That is DP, and backtracking will time out on the same input.
  • The same state is being re-explored down different branches. Memoise it, at which point it has become DP over a state.
  • Each step's choice is forced by a local rule. That is greedy, and there is nothing to back out of.

Complexity

O(branching ^ depth) in the worst case, plus O(depth) to copy out each completed solution. Space is O(depth) for the recursion and the path, output aside. Pruning is what moves the real runtime; the bound barely moves.

Variants

Subsets
include or exclude at each index
Combinations
a start index so permutations of the same set are never generated twice
Permutations
a used set, or swap-in-place and swap back
Constraint placement
conflict sets checked before descending (the n-queens shape)
Grid search
mark the cell in place, recurse, restore it
Duplicate handling
sort the candidates, then skip equal siblings at the same depth
First solution only
return a bool up the stack and stop at the first success

VIIIGreedy

The idea

Take the locally best choice at each step and never revisit it. It is the fastest thing that can possibly work.

It works only when an exchange argument holds: any optimal solution can be rewritten to begin with your choice without getting worse. No exchange argument, no greedy.

The invariant

After every step, the partial solution is still extendable to an optimal one. The sort key carries that entire claim, which is why choosing the key is the design: sort interval scheduling by finish time and the invariant holds, sort it by start time or by duration and it is false from the first step.

Solution structure

Reach for it when

  • "the maximum number of non-overlapping intervals or meetings"
  • "the minimum number of X needed to cover Y"
  • "jobs may run in any order, minimise total lateness or waiting time"
  • "repeatedly combine the two cheapest"
  • "the input is already sorted", or sorting by one obvious key makes the answer fall out
  • "the smallest lexicographic result"

Do not reach for it when

  • You cannot state the exchange argument in one sentence. Assume greedy is wrong and write the DP.
  • 0/1 knapsack by value-per-weight ratio. Correct for fractional items, wrong for indivisible ones; that is DP.
  • Coin change by largest coin first. Correct for some denomination sets and wrong for others, which is the worst kind of wrong; that is DP.

Complexity

Usually O(n log n), dominated by the sort, and O(n) when the input arrives sorted or the key buckets. O(1) extra space beyond the sort.

Variants

Earliest finish time
maximum non-overlapping intervals
Sort by start, sweep with a heap
how many rooms or workers are needed at once
Exchange-argument sequencing
shortest job first, earliest deadline first
Repeated cheapest merge
pull the two smallest from a heap and push the sum
Furthest reach
one pass tracking the best reachable point (jump and covering problems)
Fractional knapsack
by ratio, and only when items can be split

IXBinary Search

The idea

Halve the candidate range on every comparison. It applies to any predicate that is monotonic across the range - false, false, ..., false, true, true.

The range does not have to be array indices. Binary searching the answer values themselves, with a feasibility check as the predicate, is the version that wins interviews.

The invariant

The answer is always inside [lo, hi). Each iteration discards only a half proven not to contain it, and the loop ends when the range holds exactly one candidate. Half-open bounds plus lo = mid + 1 on the discarded side are what prevent both the off-by-one and the infinite loop.

Solution structure

Reach for it when

  • "a sorted array, find x, or where x would be inserted"
  • "the first or the last element that satisfies ..."
  • "the smallest capacity, speed, or budget such that everything still fits"
  • "the answer is monotonic - if x works, everything above x works"
  • "n is up to a billion", so the answer cannot be enumerated
  • "a rotated sorted array"

Do not reach for it when

  • The predicate is not actually monotonic. Binary search returns a plausible wrong answer and never errors, which makes this the most expensive misfire on the page.
  • An unsorted array and a single lookup. Use a hash set, or scan: sorting in order to binary search once costs more than the scan.
  • You are searching an array when the array is not the search space. If the input is unsorted but the answer is monotonic, search the answer range and keep the feasibility check linear.

Complexity

O(log n) comparisons over an array, O(1) space. On the answer space it is O(log(range) x cost of the feasibility check), and the check dominates: a linear check gives O(n log(range)).

Variants

Exact match
the textbook version, and the one you least often need
Leftmost boundary
lower bound, the first index not less than the target
Rightmost boundary
upper bound, the first index strictly greater
First index satisfying a predicate
the boundary form generalised past equality
On the answer space
binary search the value range with a feasibility check
Rotated array
decide which half is sorted, then discard the half that cannot hold the target
Floating point
fixed iteration count instead of an equality test
